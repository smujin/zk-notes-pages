7.kubernetes 集群网络

  • 服务器网络架构

    • 路由层：网络出口

    • 核心层：主要完成数据高效转发，链路备份等

    • 汇聚层：网络策略，安全，工作站交换机的接入，VLAN之间通信等功能

    • 接入层：工作站的接入

7.1.基础网络知识

7.1.1.交换技术
  • 交换机工作在OSI模型的第二层，即数据链数层。交换机拥有一条高带宽的背部总线交换矩阵，在同一时间可进行多个端口之间的数据传输。
  • 交换技术分为2层和3层：
    • 2层：主要用于小型局域网，仅支持在数据链路层转发数据，对工作站的接入。
    • 3层：三层交换技术诞生，最初是为了了解广播域的问题，多年发展，三层交换机已经成为构建中大型网络的主要力量。
  • OSI模型：

  • 广播域：交换机在转发数据时会先进行广播，这个广播可以发送的区域就是一个广播域。交换机之间对广播帧是透明的，所以交换机之间的网络是一个广播域。路由器下面的一个接口网络是一个广播域，所以路由器是可以隔离广播域的。

  • ARP协议（地址解析协议）：发送这个广播帧是由ARP协议实现的，ARP是通过IP地址获取物理MAC地址的一个TCP/IP 协议。

  • 三层交换机：二层交换机只工作在数据链路层，路由器则是工作在网络层。而功能强大的三层交换机可同时工作在数据链数层和网络层，并根据MAC地址或IP地址转发数据包。

  • VLAN（虚拟局域网）：VLAN是一种将局域网从逻辑上划分为一个个网段。一个VLAN就是一个广播域，VLAN之间的通信是可以通过第三层的路由器老完成的。VLAN应用广泛，基本上是大部分网络项目都会划分VLAN。

  • VLAN的主要好处：

    • 分割广播域，减少广播风暴范围。
    • 提高网络安全性，根据不同的部门，用途，应用划分不同网段。

  • 同局域网内服务器A与服务器B主机通信原理？

    • 同网段通信：基于MAC地址（请求包包含 源IP 目标IP 源端口 目标端口 源mac 目标mac等，但当前还不知道目标主机mac地址）
    • （1）如果主机A发送数据包给主机B，主机会先检查自己的ARP缓存表，查看是否有主机B的IP和mac对应关系；如果没有，主机A则会发送一个ARP请求（192.168.31.9 源MAC地址 192.168.31.10 目标MAC地址（ff-ff-ff-ff-ff-ff）)
    • （2）交换机收到数据帧之后，发现这是一个广播帧，就会将这个帧从非接收接口发送出去。
    • （3）当主机B收到数据帧之后，查询到目标IP是自己，于是就将自己MAC响应给这个ARP请求，并且记录到本地ARP缓存表
    • （4）主机收到回应的数据帧后，记录到本地ARP缓存表，然后重新封装数据帧（192.168.31.9 源MAC地址 192.168.31.10 目标MAC地址（01-00-5e-00-00-fb））+数据包

  • 如何查看ARP缓存表

    #linux查看路由，ip route
#Linux环境相同的命令，但需要安装net-tools软件包
arp -a
7.1.2.路由技术

  • 路由器是互联网的枢纽，是连接互联网中各个局域网，广域网的设备，相比交换机来说，路由器的数据转发复杂，它会根据目的的地址给出一条最优的路径，那么路径信息的来源有两种。

    • 静态路由：指人工手动指定到目标主机的地址然后记录在路由表中，如果其中某个节点不可用则重新指定。

    • 动态路由：则是路由器根据动态路由协议自动计算出路径永久可用，能实时地适应网络结构的变化。

      • 常用的动态路由协议：
        • RIP（Routing Information Protocal，路由信息协议）
        • OSPF（Open Shortest Path First，开放式最短路径优先）
        • BGP（Border Gateway Protocol，边界网关协议）

  • 路由器主要分为两个端口类型：LAN口和WAN口

    • WAN口：配置公网IP，接入到互联网，转发来自LAN口的IP数据包。
    • LAN口：配置内网IP（网关），连接内部交换机。

  • 路由器的功能：

    • （1）路由

    • （2）转发

    • （3）隔离子网

    • （4）隔离广播域

  • 不同局域网内服务器A与服务器B主机通信原理？

    • 路由表：目标地址/掩码 下一跳 接口 （有路由，转发下一跳（路由）；没有，转发默认网关（一般为路由器接口IP））
    • 如果主机A想发送数据到主机B，发现目的地的IP地址与自己不同网段，会将数据包发送给路由器，即网关（10.0.0.71 源MAC 192.168.31.72 目的MAC）
    • 路由器收到数据包，查看得知目的IP，于是查询路由表，将数据包转发给交换机（二层网络）

  • 总结：（1）同网段根据MAC地址查看主机传输数据（二层）（2）不同网段通信根据路由转发（三层）

  • TCP：TCP (Transmission Control Protocol，传输控制协议)：面向连接协议，双方先建立可靠的连接再发送数据。适用于传输数据量大，可靠性要求高的应用场景。

  • UDP (User Data Protocol，用户数据报协议)：面向非连接协议，不与对方建立连接，直接将数据包发送给对方。适用于一次只传输少量的数据，可靠性要求低的应用场景。相对TCP传输速度快

7.2.网络模型

7.2.1.docker网络模型

  • Docker网络模型涉及的名词

    • 网络的命名空间：Linux在网络栈中引入网络命名空间，将独立的网络协议栈隔离到不同的命令空间中，彼此之间无法通信，Docker利用这一特性，实现不同容器间的网络隔离。
    • Veth设备对：Veth设备对的引入时为了实现不同网络命名空间的通信。
    • Iptables/Netfilter：Docker使用Netfilter实现容器网络转发。

7.2.2.k8s网络模型

  • pod网络：

    • Pod是K8s最小调度单元，一个Pod由一个容器或多个容器组成，当一个pod中有多个容器时，怎么都用一个网络呢？

      • k8s会在每个Pod里先启动一个infra container小容器，然后让其他的容器连接进来这个网络命名空间，所以其他容器看到的网络视图就完全一样了，即网络设备、IP地址、Mac地址等。在Pod的IP地址就是infra container的iP地址。

    • pod通信有两种方式：

      • 两个pod在同一Node上
        • （1）对 Pod1 来说，eth0 通过虚拟以太网设备(veth0) 连接到 宿主机 namespace;
        • （2）网桥 cbr0 中为 veth0 配置了一个网段。一旦数据包到达网桥，网桥使用ARP 协议解析出其正确的目标网段veth1;
        • （3）网桥 cbr0 将数据包发送到 veth1;
        • （4）数据包到达 veth1 时，被直接转发到 Pod2 的network namespace 中的 eth0 网络设备；
      • 两个pod在不同Node上
        • 这就需要网络组件来实现跨主机之间的容器通信

  • CNI (Container Network Interface，容器网络接口）： 是一个容器网络规范，Kubernetes网络采用的就是这个CNI规范，负责初始化infra 容器的网络设备。

    • CNI二进制程序默认路径: /pt/cni/bin/（项目地址：https://github.com/containernetworking/cni）

    • 以Flannel网络组件为例，当部署Flanneld后，会在每台宿主机上生成它对应的CNI配置文件 (它其实是一个ConfigMap)，从而告诉Kubernetes要使用 Flannel 作为容器网络方案。（CNI配置文件默认路径: /etc/cni/net.d）

    • 当 kubelet 组件需要创建 Pod 的时候，先调用dockershim它先创建一个Infra 容器。然后调用 CNI 插件为 infra 容器配置网络。

    • 这两个路径可在kubelet启动参数中定义:

      --networkplugin=cni
--cni-conf-dir=/etc/cni/net.d
--cni-bin-dir=/opt/cni/bin

7.3.Flannal网络组件

7.3.1.VXLAN模式

  • VXLAN，即 Virtual Extensible LAN (虚拟可扩展局域网)，是 Linux 内核本身就支持的一种网络虚似化技术。VXLAN 可以完全在内核态实现上述封装和解封装的工作，从而通过与前面相似的“隧道”机制，构建出覆盖网络 (Overlay Network)。

  • 如果pod 1访问 pod 2，原地址10.244.1.10，目的地址10.244.2.10，数据包传输流程如下：

    • （1）从cantainer到cni0（容器路由）：容器根据路由表，将数据包发送下一跳 10.24.0.1，从eth0网卡出，可以使用ip route命令
    • （2）从cni0 到flannal.1（主机路由）：数据包进入到宿主机虚拟网卡cni0，根据路由表转发到flannal.1虚拟网卡。
    • （3）flannal.1封装内部数据帧：flannal.1收到IP包后，由于flannal.1工作在二层网络，二层网络又需要目的的mac地址，因此要想封装完整的二层数据帧，这个容器宿主机上flannal.1的MAC地址从哪儿获取呢？其实在flannal进程启动后，就会自动添加其他节点ARP记录，可以通过ip neigh dev flannal命令查看。
    • （4）flannal.1二次封装：知道了目的MAC地址，Linux内核就可以进行二层封包了，但是，对于宿主机网络来说，这个二层帧并不能在宿主机二层网络中传输，所以接下来，还要把这个数据帧进一步封装成为宿主机网络的一个普通数据帧，好让它载着内部数据帧，通过宿主机的eth0网卡进行传输。
    • （5）flannal.1发起UDP连接：flannal.1准备向目标容器宿主机flannal.1发起UDP连接，但这时还不知道目标宿主机是谁，也就是说这个UDP包该发给哪台宿主机呢？
      • flanneld进程也维护着一个叫做FDB的转发数据库，可以通过bridge fdb show dev flannel.1命令查看，里面记录了目标容器宿主机flannel.1的MAC对应的宿主机IP，也就是UDP要发往的目的地。接下来就是一个正常的宿主机于宿主机之间的传输了。
    • （6）数据包到达目的宿主机：数据包从Node1的eth0网卡发出去，Node2接受到数据包，封装后发现是VXLAN数据包，把它交给flannal.1设备。flannal.1设备会进一步拆包，取出原始IP包（原容器和目标容器IP），通过cni0网桥二层转发给容器。

7.3.2.HOST-GW模式

  • 当你设置flannel使用host-gw模式，flanneld会在宿主机上创建节点的路由表

    [root@k8s_master01 ~]# ip route
default via 192.168.31.1 dev ens33 proto static metric 100
10.244.0.0/24 dev cniO proto kernel scope link src 10.244.0.1
10.244.1.0/24 via 192.168.31.63 dev ens33
10.244.2.0/24 via 192.168.31.61 dev ens33
192.168.31.0/24 dev ens33 proto kernel scope link src 192.168.31.62 metric 100
    • （1）目的 IP 地址属于 10.244.1.0/24 网段的 IP 包，应该经过本机的 eth0 设备发出去(即: dev eth0)；并且它下一跳地址是 192.168.31.63(即: via 192.168.31.63) 。
    • （2）一旦配置了下一跳地址，那么接下来，当 IP 包从网络层进入链路层封装成帧的时候，eth0 设备就会使用下一跳地址对应的 MAC地址，作为该数据帧的目的 MAC 地址。
    • （3）而 Node 2 的内核网络栈从二层数据里拿到 IP 包后，会“看到”这个 IP 包的目的 IP 地址是 10.244.1.20，即 container-2的IP 地址。这时候，根据 Node 2 上的路由表，该目的地址会匹配到第二条路由规则(也就是 10.244.1.0 对应的路由规则)，从而进入 cnio 网桥，进而进入到 container-2 当中。
    • （4）可见，数据包是封装成帧发送出去的，会使用路由表的下一跳来设置目的MAC地址，会经过二层网络到达目的节点，因此，hostgw模式必须要求集群宿主机之间二层连通。

  • HOST-GW模式流程图

  • vxlan特点：先进行二层帧封装，在通过宿主机网络封装，接封装也一样，所以增加性能开销，对宿主机网络要求低，只要三层网络可达

  • host-gw特点：直接路由转发，性能损失小，对宿主机网络要求二层可达。

  • Directrouting模式：同时支持VXLAN和host-gw工作模式。

7.4.Calico网络组件

  • Calico是纯三层的数据中心网络方案，Calico支持广泛的平台，包括Kubernetes，Openstack等，Calico在每个计算节点利用Linux Kernel实现了一个高效的虚拟路由器（vRouter）来负责数据转发，而每个vRouter通过BGP协议负责把自己运行的workload路由信息向每个Calico网络内传播。此外，Calico项目实现了Kubernetes网络策略，提供了ACL功能。
  • 实际上，Calico项目提供的网络解决方案，与flannal的host-gw模式几乎一样，也就是说，Calico也是基于路由表实现容器包转发，但不同与flannal使用flannald进程来维护路由信息的做法，而Calico项目使用BGP协议来自动维护整个集群的路由信息。
  • BGP协议（边界网关协议）：它是一种自治系统间的动态路由发现协议，与其他BGP系统交换网络可达信息。

  • 在上面图中，有两个自治系统 (autonomous system，简称为AS):AS1和AS2。在互联网中，一个自治系统(AS)是一个有权自主地决定在本系统中应采用何种路由协议的小型单位。这个网络单位可以是一个简单的网络也可以是一个由一个或多个普通的网络管理员来控制的网络群体，它是一个单独的可管理的网络单元(例如一所大学，一个企业或者一个公司个体)。一个自治系统有时也被称为是一个路由选择域(routing domain)。一个自治系统将会分配一个全局的唯一的16位号码有时我们把这个号码叫做自治系统号 (ASN)。在正常情况下，自治系统之间不会有任何来往。如果两个自治系统里的主机，要通过 P 地址直接进行通信，我们就必须使用路由器把这两个自治系统连接起来。BGP协议就是让他们互联的一种方式。

  • Calico主要由三部分组成：

    • Felix：以DaemonSet方式部署，运行在每个Node节点上，主要负责维护宿主机上路由规则以及ACL规则。

    • BGP Client（BIRD）：主要负责把Felix写入Kernel的路由信息发布到集群Calico网络。

    • Etcd：分布式键值存储，保存Calico的策略和网络配置状态。

7.4.1.Calico工作模式
  • IPIP（默认配置）: Overlay Network方案，源数据包封装在宿主机网络包里进行转发和通信。
    • Pod1 访问 pod2 大致流程如下：
      • （1）数据包（原始数据包）从容器出去到达宿主机，宿主机根据路由表发送到tunl0设备（IP隧道设备）
      • （2）Linux内核IPIP驱动将原始数据包封装在宿主机网络的IP包中（新的IP包目的地只是源IP的下一跳地址，即192.168.31.63）
      • （3）数据包根据宿主机网络到达Node2
      • （4）node2收到数据包后，使用IPIP驱动进行解包从中拿到原数据包
      • （5）然后根据路由规则将数据包转发给cali设备，从而到达pod2容器

  • BGP（值设置Never）:基于路由转发，每个节点通过BGP协议同步路由表，写到宿主机（将每个宿主机当作路由器，实现数据转发）。

7.4.2路由器反射模式

  • Calico 维护的网络默认是（Node-to-Node Mesh）全互联模式，Calico集群中的节点之间都是相互建立连接，用于路由交互。但随着集群规模的扩大，Mesh模式将形成一个巨大服务网络，连接数成倍增加，将会产生性能问题。

  • 这时就需要使用 ***Route Reflector（路由器反射 RR）模式***解决这个问题，优化calico的BGP网络。

  • 确定一个或多个Calico节点充当路由反射器，集中分发路由，让其他节点从这个RR节点获取路由信息。

  • Calico 与Flannal之间的选择

    • 服务器规模大小
    • 是否可以跑BGP
    • 是否需要网络访问控制（calico支持网络策略）

  • 网络互通的情况下，办公网络直接访问k8s集群内部pod

    • 办公网络主机IP 192.168.1.212

    • k8s集群节点IP 192.168.1.123

    • 集群内部pod IP 10.244.3.129

    • 方案：直接办公网络主机上配置静态路由 10.244.3.129 -> 192.168.1.123

    route add 10.244.0.0 mask 255.255.0.0 172.16.25.36

7.5.NetworkPolicy（网络策略）

  • 默认情况下，Kubernetes集群网络没任何网络限制，Pod可以与任何其他Pod通信，在某些场景下就需要进行网络控制，减少网络攻击面，提高安全性，这就会用到网络策略。

  • 网络策略（NetworkPolicy）：是一个K8s资源，用于限制Pod出入流量，提供Pod级别和Namespace级别网络访问控制。

  • 要让网络策略生效，就需要特定的网络插件支持，目前已经实现了 NetworkPolicy 的网络插件包括 Calico、Weave 和 kube-router 等项目，但是并不包括 Flannel 项目。

  • 策略：

    • PodSelector：选择被允许访问的Pod。
    • namespaceSelector：选择被允许命名空间下的所有Pod。
    • ipBlock：被允许访问的IP地址或网段。

  • Pod隔离类型：

    • Ingress：入方向流量规则，用于配置访问服务的源地址或端口白名单。
    • Egress：出方向流量规则，用于配置Pod访问外部服务的目的地址或端口白名单

  • 限制要求：

    • 隔离 default 命名空间下具有 role=db 标签的 Pod；
    • 允许 IP 地址范围为 172.17.0.0–172.17.0.255 和 172.17.2.0–172.17.255.255 访问 default 命名空间下具有 role=db 的 Pod 的 6379 且协议为 TCP 的端口；
    • 允许具有 project=myproject 的 Namespace 下的所有 Pod 访问 default 命名空间下具有 role=db 的 Pod 的 6379 且协议为 TCP 的端口；
    • 允许 default 命名空间（和 NetworkPolicy 同一命名空间）下具有 role=frontend 标签的 Pod 访问 default 命名空间下具有 role=db 的 Pod 的 6379 且协议为 TCP 的端口；
    • 允许带有 role=db 标签的 Pod 可以访问 10.0.0.0/24 网段下的 5978 且协议为 TCP 的端口。
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy                 # 类型为NetworkPolicy
metadata:
  name: test-network-policy
  namespace: default                # 需与匹配Pod在同一个命名空间下
spec:
  podSelector:                      # 表示该策略对哪些Pod生效
    matchLabels:
      role: db
  policyTypes:                      # 网络策略的类型，如果未指定policyTypes，则默认为Ingress，如果未指定Egress，且有出口规则的话，也会配置Egress
  - Ingress
  - Egress
  ingress:                          # 入口策略配置
  - from:                           # 匹配访问来源
    - ipBlock:                      # 匹配的IP块，可以是单个IP，也可以是网段，允许的源地址地址
        cidr: 172.17.0.0/16
        except:                     # 表示从IPBlock排除一些地址，该地址允许访问
        - 172.17.1.0/24
    - namespaceSelector:            # 允许访问的命名空间
        matchLabels:
          project: myproject
    - podSelector:                  # 允许访问的Pod
        matchLabels:
          role: frontend
    ports:                          # 允许访问的端口，不配置默认所有端口可访问
    - protocol: TCP
      port: 6379
  egress:                           # 出口策略配置
  - to:
    - ipBlock:                      # 允许的访问的目的地址        
        cidr: 10.0.0.0/24
    ports:
    - protocol: TCP                 # 允许的访问的目标端口
      port: 5978
7.5.1.案例一
  • 拒绝其他命名空间Pod的访问
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy                 # 类型为NetworkPolicy
metadata:
  name: deny-all-namespaces
  namespace: test                
spec:
  podSelector: {}   #未配置，匹配本命名空间下所有Pod                   
  policyTypes:                     
  - Ingress
  ingress:                          # 入口策略配置
  - from:                           # 匹配访问来源
    - podSelector: {}      #未配置，没有匹配的白名单，表示拒绝所有Pod访问
7.5.2.案例二
  • 将test命名空间带有run=web标签的Pod隔离，只允许带有run=client标签的Pod访问80端口
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy                 # 类型为NetworkPolicy
metadata:
  name: app-to-app
  namespace: test                
spec:
  podSelector: 
    matchLabels:
      run: web 
  policyTypes:                     
  - Ingress
  ingress:                          # 入口策略配置
  - from:                           # 匹配访问来源
    - podSelector: 
        matchLabels:
          run: client
    ports:
    - protocol: Tcp
      port: 80
7.5.3.案例三

  • podSelector 没有 -，分别代表不同的配置含义：

  • 配置一的含义：允许具有 project=myproject 标签的 Namespace 下的所有 Pod 和当前 Namespace 下具有 role=frontend 标签的 Pod 访问， namespaceSelector 和 podSelector 是或的关系，满足其中之一就可以访问。
