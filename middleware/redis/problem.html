2. STS 动态字符串

STS 可能是一个特定上下文下的简称，但更普遍和著名的概念是 SDS (Simple Dynamic Strings)。它是 Redis 作者 Salvatore Sanfilippo 为 Redis 开发的一种动态字符串库，用于替代 C 语言原生的 char* 字符串。

3. List 的数据结构

Redis List 实际上有 3 种底层实现，会根据数据大小自动切换：

// Redis 源码中的定义
#define OBJ_ENCODING_QUICKLIST 4    /* 快速列表（默认） */  // QuickList = 双向链表 + 多个 ZipList
#define OBJ_ENCODING_ZIPLIST 2      /* 压缩列表（小列表） */
#define OBJ_ENCODING_LINKEDLIST 3   /* 双向链表（Redis 3.2 前） */

QuickList 的优势

// QuickList 的设计理念：
// 1. 大列表拆分成多个小 ZipList 节点
// 2. 每个 ZipList 节点存储多个元素（默认最多 8KB）
// 3. 节点之间用双向链表连接

// 内存节省示例：
// 存储 1000 个短字符串（每个10字节）
// 
// 传统链表：1000 × (24+10) = 34,000 字节
// QuickList（假设每个节点存100个元素）：
//   节点数：10个
//   节点指针：10 × 16 = 160 字节
//   数据存储：1000 × 10 = 10,000 字节
//   总内存：~10,160 字节（节省70%！）

3. Sorted Set (ZSet) 的数据结构

ZSet 有两种数据结构
a) ziplist（压缩列表）
当同时满足以下两个条件时使用：

元素数量 < zset-max-ziplist-entries （默认 128）

每个成员的长度 < zset-max-ziplist-value （默认 64 字节）

在 ziplist 中，成员和分数是紧挨着存储的两个节点，按分数排序。

b) skiplist + dict（跳跃表 + 字典）
当不满足上述条件时，自动转换为这种结构。这是一个组合数据结构：

跳跃表（skiplist）：按分数排序，支持快速的范围查询（如 ZRANGE）和排名操作。

字典（dict）：实现 O(1) 时间复杂度的成员到分数的查找（如 ZSCORE）。

这种双重结构确保了 ZSet 在任何操作上都有优异的性能

跳表的是多个层级的，但是第一层就是一个链表，链接所有数据，其他层级分别指向不同的跳跃位置，这样查询时从最上面层开始查询，上层查不到再往下层查，然后逐层往下查，直到找到为止。 找到了以后再去字典表中查找对应的分数。这样兼顾性能和空间。

4. 缓存穿透

4.1 缓存穿透是指查询一个数据库和缓存中都不存在的数据（如查询 ID = -1 的数据，或随意编造的不存在 ID） 解决方法：缓存空数据，即缓存一个空对象，或者缓存一个错误码，这样当用户查询不存在的数据时，会返回错误码，而不是空对象。或者 过滤掉不合适的值

5. 缓存击穿

5.1 缓存击穿是指某个热点 key 在缓存中过期（失效）的瞬间，同时有大量的请求并发访问这个 key。所有请求发现缓存失效，都会去数据库查询并回设缓存，导致数据库瞬间压力激增，就像被“击穿”了一样。

解决方案：

5.2 热点数据永不过期：

对真正的极热点数据，可以设置逻辑上的永不过期（即不设置过期时间，或过期时间非常长）。

同时，启动一个后台定时任务，定期异步地更新这个缓存。这样就不会有“过期瞬间”的问题。

缺点：需要额外的维护逻辑，占用内存。

5.3 互斥锁：

当缓存失效时，不是所有线程都去查询数据库，而是让一个线程（如使用 Redis 的 SETNX 命令实现分布式锁）去查询数据库并重建缓存，其他线程等待锁释放后，直接从新缓存中读取数据。

优点：能有效防止数据库被压垮。

缺点：性能有损耗，可能出现线程等待。如果获取锁的线程挂掉，可能需要处理锁超时。

6. 缓存雪崩

6.1 缓存雪崩是指在同一时间段内，大量的缓存 key 同时失效或 Redis 服务宕机，导致所有请求都涌向数据库，造成数据库瞬时压力过大而崩溃，继而引发整个系统雪崩式的连锁故障。

解决方案：

6.1 设置随机的过期时间：

避免大量 key 在同一时间过期。在设置缓存过期时间时，在原定过期时间上加上一个随机值（如 1-10 分钟的随机数），让 key 的失效时间点均匀分布。

// 伪代码：设置缓存时，过期时间 = 基础时间 + 随机时间
int expireTime = 3600 + Random.nextInt(600); // 3600 ~ 4200 秒之间
cache.set(key, data, expireTime);

6.2 构建高可用缓存集群：

使用 Redis 哨兵（Sentinel）或集群（Cluster）模式，防止单点故障导致整个缓存服务不可用。

必要时可做异地多活。

6.3 服务降级与熔断：

在非核心业务或非关键数据查询时，如果缓存失效，可以采用服务降级策略，比如返回默认值、兜底数据，或者直接使用缓存中的旧数据，而不是直接访问数据库。

配合 Hystrix、Sentinel 等熔断器组件，当检测到数据库访问异常或超时比例过高时，自动熔断，快速失败，保护数据库。

6.4 提前预热：

对于已知的热点数据，可以在系统上线或高峰来临之前，提前将其加载到缓存中，并设置好错峰的过期时间。

6.5 双层缓存策略：

使用本地缓存（如 Caffeine、Guava Cache）作为一级缓存，Redis 作为二级缓存。

一级缓存过期时间更短，二级缓存更长。当 Redis 崩溃时，本地缓存还能支撑一段时间，给 Redis 恢复留出时间。
