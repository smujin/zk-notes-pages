1. volatile 的作用

volatile 是一个轻量级的同步机制。它主要解决两个问题：内存可见性 和 禁止指令重排序。它不能保证原子性。

作用一：保证内存可见性

问题所在（无 volatile 的情况）：

  1. 内存结构：在多核 CPU 架构下，每个线程都有自己的工作内存（CPU 高速缓存），它们会从主内存中拷贝变量的副本进行操作。
  2. 可见性问题：当一个线程修改了自己工作内存中的变量副本后，如果没有特殊的同步机制，这个修改可能不会立即写回主内存，其他线程也就无法看到这个最新的值，导致它们仍然在使用旧的、过期的值。

volatile 的解决方案： 当一个变量被声明为 volatile 后：

  • 写操作：当写一个 volatile 变量时，JMM（Java 内存模型）会立即将该线程工作内存中的新值刷新到主内存中。
  • 读操作：当读一个 volatile 变量时，JMM 会使该线程的工作内存中的副本失效，从而强制它必须从主内存中重新读取最新的值。

简单比喻：

  • 普通变量：就像办公室里的公告板，有人更新了内容，但其他人可能还在看自己之前拍的照片（缓存副本）。
  • volatile 变量：就像一块所有人都必须亲自去看的实时电子公告板，任何更新对所有人都是立即可见的。

代码示例（可见性问题）：

public class VisibilityProblem {
    // 如果没有 volatile，线程可能永远无法看到 stop 被改为 true
    private static /*volatile*/ boolean stop = false;

    public static void main(String[] args) throws InterruptedException {
        Thread backgroundThread = new Thread(() -> {
            int i = 0;
            while (!stop) { // 如果 stop 的更新不可见，这个循环可能不会结束
                i++;
            }
            System.out.println("背景线程结束");
        });
        backgroundThread.start();

        Thread.sleep(1000); // 主线程休眠1秒
        stop = true; // 1秒后，主线程修改 stop 的值
        System.out.println("主线程设置 stop 为 true");
    }
}

运行上述代码，你可能会发现程序无法停止（取决于你的 JVM 和操作系统）。但给 stop 加上 volatile 后，程序就能正常结束。

作用二：禁止指令重排序

问题所在： 为了优化性能，编译器和处理器常常会对指令的执行顺序进行重排序。在单线程环境下，这不会影响最终结果（遵循 as-if-serial 语义）。但在多线程环境下，重排序可能导致意想不到的问题。

经典的例子：双重检查锁单例模式

我们再看一下有问题的代码：

public class SingletonDCL {
    private static SingletonDCL instance; // 缺少 volatile

    private SingletonDCL() {}

    public static SingletonDCL getInstance() {
        if (instance == null) { // 第一次检查
            synchronized (SingletonDCL.class) {
                if (instance == null) { // 第二次检查
                    instance = new SingletonDCL(); // 问题出在这一行！
                }
            }
        }
        return instance;
    }
}

instance = new SingletonDCL(); 这行代码并不是一个原子操作，它实际上包含了三个步骤：

  1. memory = allocate(); // 1：为对象分配内存空间
  2. ctorInstance(memory); // 2：初始化对象（调用构造方法）
  3. instance = memory; // 3：将 instance 引用指向刚分配的内存地址

步骤 2 和 3 可能会被重排序！ 变成：

  1. 分配内存
  2. 将引用指向内存地址（此时 instance 不为 null，但对象还未初始化！）
  3. 初始化对象

这会引发什么？ 假设线程 A 执行到了 getInstance()，它进入了同步块，并开始创建对象。如果发生了重排序，它刚执行完步骤 2（instance 已不为 null）但还未执行步骤 3（对象未初始化）时，线程切换发生了。

此时线程 B 执行 getInstance()，它在第一次检查 if (instance == null) 时，发现 instance 已经不为 null（因为线程 A 已经执行了步骤2），于是直接返回了这个 instance。但此时线程 B 拿到的是一个未初始化完成的、半成品的对象！使用它就会导致错误。

volatile 的解决方案： 使用 volatile 修饰 instance 变量后，JVM 会通过在指令序列中插入内存屏障 来禁止对 volatile 写操作之前的任何读写操作与它进行重排序，同时也禁止对 volatile 读操作之后的任何读写操作与它进行重排序。

这就保证了 instance = new SingletonDCL(); 这个写操作之前的指令（对象初始化）一定已经完成，并且对其它线程是可见的。

2. volatile 是如何实现其作用的？

volatile 的实现深度依赖于底层硬件和 JVM。

1. 内存屏障

内存屏障是一组 CPU 指令，用于控制对内存操作的顺序。volatile 的实现正是通过在生成的汇编指令中插入特定的内存屏障来实现的。

主要的内存屏障有：

  • LoadLoad屏障：确保该屏障之前的读操作先于之后的读操作完成。
  • StoreStore屏障：确保该屏障之前的写操作先于之后的写操作完成，并且之前的写操作结果对其他处理器可见。
  • LoadStore屏障：确保该屏障之前的读操作先于之后的写操作完成。
  • StoreLoad屏障：这是一个“全能型”屏障，它同时具有其他三种屏障的效果，开销也最大。volatile 写操作之后会插入一个 StoreLoad 屏障。

JVM 对 volatile 内存屏障的插入策略（简化版）：

  • 在 volatile 写操作之前：插入一个 StoreStore 屏障，防止上面的普通写与 volatile 写重排序。
  • 在 volatile 写操作之后：插入一个 StoreLoad 屏障，防止 volatile 写与下面可能有的普通读/写重排序，并保证写结果能立刻对其他线程可见。
  • 在 volatile 读操作之前：插入一个 LoadLoad 屏障，防止下面的普通读与 volatile 读重排序。
  • 在 volatile 读操作之后：插入一个 LoadStore 屏障，防止下面的普通写与 volatile 读重排序。

2. 缓存一致性协议（如 MESI）

现代多核 CPU 都实现了缓存一致性协议来保证各个核心的缓存数据是一致的。

  • 当 CPU 核心修改了其缓存中一个被标记为 volatile 的变量时，这个修改会通过总线通知给其他核心。
  • 其他核心会将自己缓存中对应的数据行标记为 “无效” 状态。
  • 当其他核心需要读取这个变量时，发现自己缓存中的数据是无效的，就会被迫从主内存（或其他核心的缓存）中重新加载最新的数据。

这个过程是由硬件直接支持的，volatile 关键字触发了这一机制。

总结与注意事项

什么时候使用 volatile？

  1. 对变量的写操作不依赖于当前值（例如 flag = true），或者你能确保只有单一线程修改变量值。
  2. 该变量不会与其他变量一起纳入不变性条件中。
  3. 在访问变量时不需要加锁。

典型场景：

  • 状态标志位（如上面的 stop 示例）。
  • 双重检查锁单例模式中的实例引用。
  • Disruptor 等高并发框架中广泛使用 volatile 来维护内存可见性。
